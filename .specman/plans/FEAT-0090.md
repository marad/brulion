# Sync plan — FEAT-0090 Workbench freshness and release validation

Started: 2026-08-08T21:28:39.414Z
Snapshot state: new
Drift summary: 5 added (whole spec)

## AC-1 (added): Given the workbench attaches, opens, or regains focus, when it refreshes,
  then its tree and diagnostics reflect the current filesystem state.

Approach: Keep refresh ownership in the workbench window, but route attach, manual,
focus, and timer triggers through a small serialized/coalescing refresh scheduler
exported from `workbench.ts`. The existing generation-aware filesystem refresh
rereads manifests, supported files, and mtimes before repainting the selected file.

Files:
`src/workbench.ts`, `src/workbench-main.ts`, `src/workbench.test.ts`.

## AC-2 (added): Given another window or agent edits a file between read and save, when
  the workbench saves, then the mtime conflict is shown and disk bytes are
  preserved.

Approach: Retain the per-file `lastModified` guard in `writeScriptFile` and add
contract tests at the storage and Chromium layers for both a stale save and a
refresh that preserves a dirty draft instead of replacing it with external bytes.

Files:
`src/script-storage.ts`, `src/script-storage.test.ts`, `src/workbench-main.ts`,
`e2e/extensions.spec.ts`.

## AC-3 (added): Given an extension is edited and explicitly reloaded, when reload fails,
  then the failure is diagnosed and the notes editor and other extensions remain
  usable.

Approach: Keep reload explicit at the existing `ExtensionRegistry.load` boundary;
its generation token disposes stale runners, `Promise.allSettled` isolates failed
scripts, and `onError` reports the failed script. Add a regression test proving a
failed reload does not remove a healthy extension's actions or reject the registry
load.

Files:
`src/extension-registry.ts`, `src/extension-registry.test.ts`, `src/main.ts`.

## AC-4 (added): Given no FileSystemObserver support, when the fallback cadence runs, then
  the workbench still converges by polling/rescanning without changing
  correctness semantics.

Approach: The scheduler uses ordinary `setInterval` polling with a bounded
3-second cadence, coalesces overlapping requests, and has no observer or IPC
branch. A scheduler unit test proves one refresh at a time and a queued trigger
is not lost.

Files:
`src/workbench.ts`, `src/workbench-main.ts`, `src/workbench.test.ts`.

## AC-5 (added): Given a real Chromium vault, when a user creates, edits, saves, enables,
  and runs a multi-file extension, then browser tests cover the flow, including
  a second-window/external-edit conflict scenario.

Approach: Extend the OPFS Chromium suite with the release path: create and edit a
multi-file extension, enable it through the separate manager, run its command,
refresh after an external edit, preserve a dirty draft, and assert a stale save
leaves the external bytes intact. Keep the second-window boundary filesystem-only.

Files:
`e2e/extensions.spec.ts`, `src/workbench-main.ts`, `src/extension-registry.ts`.
