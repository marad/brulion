## AC-1 (added): Given an alert, confirm, or prompt with valid plain or formatted
  `MessageContent`, when it opens, then the host modal contains only host-owned
  text/strong/code/br nodes, shows the supplied plain-text labels, and renders
  semantic newlines without interpreting HTML, Markdown, links, or nested
  values.

Approach: Extend the existing dialog adapter with a shared safe message-render
hook and explicit per-call labels/options. Keep the renderer in the P2
interaction module and preserve the plain-string application dialog API through
an adapter normalization layer.

## AC-2 (added): Given a confirm call, when the user presses its labeled confirm or
  cancel button, Escape, or the allowed backdrop dismissal, then the RPC
  resolves respectively to `true` or `false`; labels identify the buttons and
  no other modal surface is dismissed.

Approach: Add a modal request type with explicit mode and labels, route button,
Escape, and backdrop events through one close path, and expose a source-scoped
extension dialog adapter over the existing host dialog lifecycle. Keep conflict
and other backdrop ownership unchanged.

## AC-3 (added): Given a prompt with single-line or multiline options, initial text,
  placeholder, and either outcome, when the user confirms or cancels, then the
  host uses the requested input control, preserves the initial/placeholder
  values, returns the exact entered UTF-16 string or `null`, and distinguishes
  accepted empty text from cancellation.

Approach: Add a textarea mount point or controlled input/textarea swap to the
existing dialog DOM, keeping one logical field and one focus-restore path.
Represent prompt result as string|null; do not infer cancellation from empty
text. Enter submits only the input variant; textarea permits semantic newlines.

## AC-4 (added): Given a dialog call with malformed/oversized message, unknown option,

  when it crosses the host boundary, then it rejects before opening a modal or
  invoking the dialog adapter.

Approach: Retain FEAT-0102 strict host validators and add no validation bypass
in the UI adapter. Extend host tests for prompt confirmLabel, multiline,
unknown fields, and no-callback behavior; use the existing permission gate.

## AC-5 (added): Given multiple dialog requests while another Brulion modal or extension
  dialog is active, when they are answered in sequence, then they are FIFO,
  exactly one modal is visible, and focus is restored after each completed
  request without starving a queued request.

Approach: Generalize the existing dialog queue to explicit request records and
queue them alongside existing app calls. The extension adapter awaits the same
queue rather than creating a second backdrop. One close function promotes the
next request only after restoring the prior focus.

## AC-6 (added): Given an extension with an active or queued dialog, when it is disabled,
  disposed, or its vault is detached, then the active UI closes, queued and
  active RPC calls reject immediately with `disposed`, focus is restored, and
  no callback or late response can affect a replacement extension/vault.

Approach: Give the extension dialog adapter source-scoped cancellation handles
registered with ExtensionHost's existing optional interaction dispose seam.
Extend dialog destroy/cancel to reject queued extension records without
cancelling unrelated application dialog requests. Keep RPC peer shutdown as the
last line of runner disposal so host cleanup happens before transport close.

## AC-7 (added): Given an unanswered dialog, when the human-scale deadline expires,
  then the sandbox receives a coded `timeout` rejection, the host closes and
  cleans up the associated modal, and a later dialog can open normally.

Approach: Preserve the method-specific 120,000ms child timeout and coded RPC
error from P0. Add a deterministic short-timeout injectable to the browser/
transport test seam rather than waiting two minutes; on timeout the host modal
adapter closes the source request through its cancellation path.

## AC-8 (added): Given a real Chromium/OPFS enabled extension, when user-invoked commands
  call alert, confirm, and prompt, then the browser observes formatted content,
  custom labels, both confirm outcomes, single-line/multiline input, empty vs
  cancelled prompt results, disposal/timeout cleanup, and unchanged Markdown
  bytes through the real iframe/RPC path.

Approach: Add a dedicated Playwright OPFS fixture with the dialogs permission
and commands that register result actions after each user response. Drive the
host modal controls as a user would and assert the result action labels plus
raw note bytes. Exercise disabling/removing the extension or vault switch for
cleanup; keep native OS dialogs out of the test.
