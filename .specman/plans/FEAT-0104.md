# Sync plan — FEAT-0104 Formatted extension notifications

## AC-1 (added): Given a valid plain message or `MessagePart[]`, when the host renders
  it into a notification, then text, strong, and code fragments appear as
  host-created nodes, every newline appears as a `<br>`, and the visible text
  matches the source exactly without `innerHTML` or Markdown interpretation.

Approach: Add a small host-only message renderer that accepts the already
validated `MessageContent` union and appends text, strong, or code elements plus
line-break nodes. Keep the renderer independent of RPC, extension source, and
Markdown parsing so dialogs can reuse it in FEAT-0105.

Files:
- src/extension-interactions.ts
- src/extension-interactions.test.ts

## AC-2 (added): Given message content containing HTML-looking text, links, nested
  objects, unsupported part types, or values outside the P0 bounds, when
  `notifications.show()` is called, then the host rejects before rendering and
  the notification region and editor remain unchanged.

Approach: Leave shape/size rejection at ExtensionHost's P0 validator and test
that the notification callback is not reached on invalid wire values. Add
renderer tests with hostile-looking strings to show they remain text nodes and
never create links or nested markup.

Files:
- src/extension-host.test.ts
- src/extension-interactions.test.ts

## AC-3 (added): Given an enabled extension with the `notifications` permission, when
  it calls `notifications.show()` with each severity and with omitted options,
  then a host-owned toast appears with the matching level (or `info` by
  default), safe attribution, and an accessible dismiss control; given no
  permission, the injected notification callback is not called.

Approach: Implement a NotificationCenter mounted on a dedicated live region.
The host binds the extension id as attribution in the internal callback seam;
the public RPC never receives arbitrary attribution. Wire the center through
ExtensionRegistry and main's captured-vault callback while preserving the
existing permission gate.

## AC-4 (added): Given a notification call, when it is accepted, then the RPC resolves
  after enqueueing without waiting for auto-dismissal, keyboard focus remains
  on the previously focused element/editor, and no Markdown document, mtime,
  selection, or save callback changes.

Approach: Make `show()` synchronous/fire-and-forget at the host adapter and
return immediately from the async RPC handler after enqueueing. Never focus a
new node; use an explicit close button without autofocus. Cover focus, promise
settlement before timers, and unchanged editor state in unit tests.

Files:
- src/extension-interactions.ts
- src/extension-interactions.test.ts
- src/extension-host.test.ts

## AC-5 (added): Given more than three visible notifications and queued notifications,
  when they are shown and dismissed or expire, then only three are visible,
  queued items are promoted FIFO, the ninth excess item is dropped, and no
  unbounded DOM/timer growth occurs.

Approach: Keep per-center FIFO queues with MAX_VISIBLE=3 and MAX_QUEUED=8.
Drop incoming items when both caps are full. Use one auto-dismiss timer per
visible toast and promote queue items on close; manual and timer closes share
one idempotent path.

- src/extension-interactions.ts
- src/extension-interactions.test.ts

## AC-6 (added): Given an extension runner is disposed or its captured vault is
  detached, when its notifications are pending or visible, then its owned
  notifications are removed, later stale calls reject before enqueueing, and
  another active vault/extension's notifications are not removed by a
  different source disposal.

Approach: Track each toast's extension source id and expose a source-scoped
clear/dispose callback through the internal interaction seam. Main's captured
root guard rejects stale calls; registry/host disposal calls the source cleanup
without touching other source ids.

## AC-7 (added): Given a real Chromium page with an OPFS-backed enabled extension, when a
  user-invoked command calls `notifications.show()` with formatted content,

Approach: Extend the existing OPFS extension fixture with the notifications
permission and a user-invoked command. Assert the host toast's level,
formatted DOM, attribution, dismissal, and unchanged note bytes through the
real sandbox/RPC path.
