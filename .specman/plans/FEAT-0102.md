## AC-1 (added): Given the checked-in v1 contract, declarations, API reference, host
  allowlist, and sandbox bootstrap, when their interaction surface is
  enumerated, then `editor.setSelection`, `notifications.show`, and all three
  `dialogs.*` methods appear exactly once with matching names, signatures,
  result types, and permissions, and no undocumented interaction RPC exists.

Approach: Extend the single host method inventory and the public sandbox API in
lockstep, then update the typed declarations, JSON contract, and prose reference
from the same method/type/permission decisions. Keep existing method ids and API
version unchanged so this is additive.

## AC-2 (added): Given an existing manifest that omits every new M46 permission, when it
  is parsed and activated, then it remains valid and all previously granted
  command, editor, notes, and navigation methods retain their old behavior;
  given `editor:read` without `editor:selection`, `notifications` without
  `dialogs`, or `dialogs` without `notifications`, then each ungranted M46
  method rejects before its injected host callback runs.

Approach: Add only the new least-privilege permission literals to the manifest
allowlist and gate each new host handler independently. Preserve existing
permission mappings and make the host default safe for the new methods. Add
manifest and host tests that exercise omitted and split grants without invoking
application callbacks.

## AC-3 (added): Given a valid selection result or `setSelection` request, when it crosses
  the host boundary, then it uses only `{ anchor, head, text }` or
  `{ anchor, head }`, preserves reverse direction and collapsed cursors, and
  rejects non-integer, negative, out-of-document, or extra-field values without
  calling the editor callback.

Approach: Replace the public selection shape with anchor/head, add a bounded
host-side request validator with an injected editor callback, and leave document
content writes on the existing replacement capability. The document-length
check belongs at the application/editor adapter, while the host rejects wire
shape and safe-integer violations before that callback.

## AC-4 (added): Given a message value, when it is validated, then plain strings and
  `text`/`strong`/`code` parts with semantic newlines are accepted within the
  part and total bounds, while empty parts arrays, unknown kinds, nested or
  extra fields, non-strings, overlong fragments, and overlong totals reject
  before rendering.

Approach: Define shared MessageContent/MessagePart wire types and one strict
validator in the host boundary. Normalize accepted strings and part arrays into a
bounded host value without interpreting HTML or Markdown. Keep renderer work out
of this phase; later phases consume the validated value.

## AC-5 (added): Given notification or dialog options, when they cross the host
  boundary, then only the documented severity, bounded labels, prompt values,
  and boolean multiline flag are accepted; every visible button has a supplied
  plain-text label, unknown fields and HTML-shaped values reject, and prompt
  cancellation remains distinguishable from an accepted empty string.

Approach: Add explicit notification and dialog option/result types, strict option
parsers, and permission-gated host callback seams. Require per-button labels and
keep prompt cancellation as null in the API contract; defer actual DOM and queue
bodies to FEAT-0104/0105.

## AC-6 (added): Given an interactive dialog call, when a human answers before the
  deadline, then the result travels over the existing nonce-bound RPC as a
  JSON-like value; when the deadline expires, the call rejects with `timeout`,
  and the ordinary 5-second deadline is not used for the dialog request.

Approach: Keep the ordinary RPC timeout for all existing methods and introduce a
named human-scale dialog deadline used by the child bootstrap for dialogs only.
Document the exact milliseconds in the runtime contract and preserve the existing
nonce/version and JSON-like validation rules.

## AC-7 (added): Given an active or queued dialog belonging to an extension, when the
  runner is disposed or its vault becomes stale, then the host closes its
  extension-owned modal state, restores prior focus, rejects/settles all
  associated work with `disposed`, and does not leave a pending RPC or invoke
  an application callback after disposal.

Approach: Define the lifecycle/error contract and disposal hook at the host/runner
seam, so dialog adapters can later register cancellation with the owning host.
Ensure peer disposal rejects pending calls and prevents late responses; leave the
existing application dialog's unrelated lifecycle unchanged until the dialog
adapter phase.

## AC-8 (added): Given the sandbox bootstrap and a hostile message fragment or dialog
  label, when the public API is rendered or inspected, then the host uses
  text/line-break nodes and host-owned elements only; extension HTML, links,
  DOM references, CodeMirror values, filesystem handles, and system notification
  APIs never cross the boundary.

Approach: Expose only frozen JSON-like methods and documented value types from the
bootstrap. Add contract/bootstrap tests for the new namespaces and explicitly
keep the HTML/DOM renderer outside the child context; host validators reject
markup-shaped object values and arbitrary fields.
