## Intent

Make the primary CodeMirror note editor consume the M47 rich Markdown model
without making the visible projection the file format. The editor boundary owns
conversion between visible CodeMirror text and a loss-aware `RichDocument`; it
exposes a serialized Markdown snapshot to storage, autosave, conflicts, and
extensions while preserving the source bytes that the model did not intend to
change. Existing note-controller operations must therefore work from serialized
Markdown rather than from `view.state.doc.toString()`.

## Behavior

Loading a note imports its Markdown into the rich document and puts the model's
visible projection in the primary CodeMirror view. A programmatic load is not a
user edit. User changes are applied against visible positions, re-imported into
the model, and projected back into CodeMirror; the editor boundary keeps the
current serialized source snapshot separately from the visible text. A source
conversion such as a completed `**hello** ` remains one logical editor change,
while its serialized form remains `**hello** ` and untouched source spans retain
original bytes.

The controller reads the serialized snapshot for every save, conflict version,
cache entry, and dirty decision. Lazy `start.md` creation, note switching,
rename/move follow-up loads, and all conflict resolution paths use the same
boundary. External Markdown is imported again rather than inserted as raw
source; when the active buffer is clean, the visible caret and top viewport
anchor are mapped through the reparse and retained as far as the new source can
map them. When local serialized edits exist, external changes raise the existing
conflict state and neither side is discarded.

Unknown syntax and opaque special blocks remain source-owned. A normal visible
edit cannot serialize rendered output or silently normalize unrelated source;
explicit P4 source-edit operations are the only route through those islands.
Other CodeMirror editors, including the workbench and conflict diff, remain raw
text editors and do not acquire the primary editor's rich boundary.

## Acceptance criteria

- AC-1: Given Markdown loaded into the primary note editor, when the load
  completes, then the CodeMirror document contains the rich visible projection,
  the editor boundary exposes the exact serialized Markdown snapshot, and a
  programmatic load does not mark the note dirty or call the autosave callback.
  Visible positions never expose hidden Markdown delimiters as normal caret
  text.
- AC-2: Given a user edit expressed in visible CodeMirror positions, when the
  boundary applies it, then the rich model is re-imported/projected and its
  serialized snapshot is used for the next save. Completed input rules such as
  `**hello** ` preserve `**hello** ` in the snapshot while showing `hello `;
  one user action remains one undo/history unit, and incomplete markers remain
  editable rather than being silently dropped.
- AC-3: Given an imported note containing Unicode, CRLF, unknown syntax, links,
  fences, tables, frontmatter, Mermaid, or nested marks, when it is loaded and
  serialized without an intentional source edit, then the bytes are identical.
  A visible edit changes only its mapped source span; opaque/special source and
  unrelated delimiter spelling, whitespace, and line endings are retained.
- AC-4: Given a dirty primary editor, when autosave, blur/visibility flush, or
  explicit save runs, then `saveNote` receives the current serialized Markdown
  snapshot and the last-seen mtime, never the visible CodeMirror projection.
  Lazy creation of an absent `start.md` writes the serialized source and updates
  the cache/list only after the guarded save succeeds.
- AC-5: Given a note switch, add, delete, rename, or folder move, when the
  controller flushes or reloads the affected note, then it serializes the
  current model before the operation, loads the destination through the same
  rich boundary, and never leaves a visible projection paired with another
  note's source/mtime/cache entry. Move and rename follow-up link maintenance
  still receives the raw Markdown snapshot.
- AC-6: Given a clean active buffer and a changed Markdown file on disk, when
  external refresh runs, then the new file is imported and projected without
  treating the refresh as a user edit; the visible caret and top viewport anchor
  are mapped through the reparse where possible, the serialized snapshot and
  mtime adopt disk, and no stale model is subsequently saved.
- AC-7: Given an active buffer whose serialized snapshot differs from the last
  saved snapshot, when the disk file changes or disappears, then the controller
  raises the existing conflict with the serialized `mine` and current on-disk
  `theirs`, locks the editor, and does not overwrite or discard either side
  before the user chooses. Keep-mine and take-theirs rebase/reload through the
  boundary and clear dirty/conflict state only after the guarded result succeeds.
- AC-8: Given raw-source consumers such as the extension API or an explicit P4
  source-edit operation, when they request or mutate Markdown, then they receive
  serialized source and UTF-16 source coordinates, not visible projection
  coordinates; stale/cross-node edits are rejected and rendered/visible text is
  never written as a substitute for Markdown.
- AC-9: Given a workbench editor or a read-only conflict diff, when it loads or
  edits text, then it remains a normal raw CodeMirror document and is not routed
  through the primary note editor's rich state or serialization boundary.
- AC-10: Given invalid visible/source positions, a failed reparse, or a stale
  source/model request, when the boundary or controller handles it, then it
  rejects the operation without writing, losing the prior valid model, or
  falsely clearing dirty/conflict state; the existing stale-write guard remains
  the final authority before disk mutation.

## Out of scope

- visible selection/clipboard serialization, slash-command and formatting
  command adapters, link autocomplete, heading-anchor adapters, and Vim
  translation; these are FEAT-0114;
- final removal of the old renderer/decorations and full Chromium/OPFS migration;
  these are FEAT-0115;
- changing FSA permissions, note ownership, vault identity, or storage format;
- whole-document Markdown normalization, metadata interpretation, rendered HTML
  clipboard interoperability, or silently deleting unsupported syntax;
- routing workbench, merge/diff, extension-script, or other secondary
  CodeMirror editors through the primary rich model.
