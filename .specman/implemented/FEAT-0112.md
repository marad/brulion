## Intent

Move the remaining Markdown constructs across the loss-aware rich-document
boundary without making their source bytes disposable. Standard Markdown links
and wikilinks become typed rich link nodes whose labels are visible while their
targets remain available only through an explicit source-edit operation. Fenced
code, tables, frontmatter, and Mermaid become typed opaque special blocks: the
model records their exact source span and useful metadata, but does not pretend
that a rendered widget or a parsed table cell is a lossless replacement for the
source. This gives later CodeMirror view adapters a single, source-map-owned
contract while keeping incomplete or ambiguous syntax raw and editable.

## Behavior

A complete inline Markdown link (`[label](destination)`) or wikilink
(`[[target]]` / `[[target|alias]]`) is recognized only when its delimiters and
non-empty label/target are complete on one line. The visible projection contains
the label, with link metadata and source ranges for the label and target; the
brackets, destination, and wikilink target syntax are not visible caret stops.
Bare web URLs remain visible link nodes without hidden source. Link labels may
contain the existing inline marks, but links and targets are never parsed inside
fences, tables, frontmatter, Mermaid, comments, or other opaque regions. An
explicit link-source operation can replace only a target or label span and
preserves all surrounding spelling, whitespace, alias syntax, and unrelated
source.

A closed fenced block is recognized as one typed special span, retaining the
opening/closing character, exact fence length, indentation, info-string bytes,
body, and line endings. Its source remains an opaque editable island in the rich
model; no inline Markdown is parsed inside it, and an unclosed fence stays raw.
Entering or leaving a fence is an explicit source-editing action, not an
implicit cursor-line reveal or a conversion that can consume code text.

A contiguous table is recognized only after a header row and a valid separator
row, with body rows kept in the same source span. Detection records exact row
and cell source ranges, alignment hints, and raw cell text without trimming or
re-serializing it. Escaped pipes and uneven rows are either mapped safely or
left as an opaque non-table line. Table cell edits use an explicit source-range
operation; they change only the chosen cell's text and never normalize pipes,
spacing, alignment, or neighboring rows.

A leading, closed `---`/`---` or `...` block is a typed opaque frontmatter span.
It is expandable through an explicit source-editing affordance, but field names
and values are never interpreted or reserialized. A closed fenced block whose
info string is `mermaid` (case-insensitive, with surrounding info whitespace
ignored) is additionally typed as Mermaid; rendering and asynchronous parse
errors are view concerns, while source editing replaces only the original
Mermaid source span. All special blocks preserve their untouched bytes exactly.

## Acceptance criteria

- AC-1: Given a complete one-line `[label](destination)` or `[[target]]` /
  `[[target|alias]]`, when Markdown is imported, then the visible projection
  contains only its label, a typed link node records kind/label/target source
  ranges, and `visibleToSource`/`sourceToVisible` map UTF-16 positions without
  exposing bracket, destination, or wikilink delimiter caret stops. Incomplete,
  empty, multiline, malformed, or ambiguous link syntax remains an opaque raw
  region.
- AC-2: Given a link label containing supported inline marks or a bare `http://`,
  `https://`, or `www.` URL, when it is imported, then the label/URL remains
  visible with link metadata and nested marks where safe; links inside a fence,
  table, frontmatter, Mermaid, HTML comment, or unknown opaque region are not
  parsed as links.
- AC-3: Given an imported Markdown link or wikilink, when an explicit link-source
  edit changes its label or target, then only that exact source span is replaced,
  aliases, delimiters, whitespace, escaping, line endings, and unrelated source
  remain unchanged, and a normal visible edit cannot accidentally rewrite a
  hidden target or cross a link node boundary.
- AC-4: Given a closed fenced block with backtick or tilde delimiters, when it is
  imported, then one typed fence node records the exact raw span, delimiter
  character/count, info string, and body; inline markers inside the body remain
  literal, and an unclosed or mismatched fence remains raw. Explicit fence source
  editing can replace the block without normalizing untouched bytes, and Enter
  in the block does not create a rich paragraph or consume fence markers.
- AC-5: Given a header row followed by a valid pipe separator and contiguous body
  rows, when it is imported, then one typed table node records exact row/cell
  ranges and separator alignment without changing the visible source or raw
  spelling. Escaped pipes, blank separators, fences, and ambiguous rows are not
  guessed into a table. An explicit cell edit changes only that cell's source
  range and preserves all other table bytes.
- AC-6: Given a leading closed frontmatter block, when it is imported, then it is
  one opaque frontmatter node with an explicit expand/source-edit state, no
  metadata field is interpreted, and serialization is byte-identical until an
  explicit source edit. A non-leading or unclosed delimiter is not frontmatter.
- AC-7: Given a closed fenced block whose info string is `mermaid` in any case,
  when it is imported, then it is typed as Mermaid while retaining the complete
  fence/source span; rendering is optional view metadata, parse failure cannot
  replace source, and explicit editing never serializes rendered HTML/SVG.
- AC-8: Given Unicode text, CRLF input, nested inline marks, adjacent special
  blocks, unknown syntax, or edits at source/visible boundaries, when the model is
  mapped and serialized, then all offsets remain UTF-16 deterministic, untouched
  bytes and line endings survive exactly, no special construct is silently
  dropped or normalized, and every explicit operation is one loss-aware source
  change.
- AC-9: Given a special block or link at the caret, when selection/caret movement
  occurs, then no behavior depends on revealing raw syntax merely because the
  caret entered the construct; source editing is available only through the
  explicit operation exposed by the rich-model boundary.

## Out of scope

- note-path resolution, navigation, link autocomplete, persistence, conflict
  handling, clipboard, Vim, extension translation, and browser validation;
- rendering widgets or Mermaid's asynchronous SVG engine themselves (view
  adapters consume this model in later integration phases);
- interpreting frontmatter fields, normalizing Markdown, or HTML clipboard
  interoperability;
- replacing CodeMirror or introducing Tiptap/ProseMirror.
