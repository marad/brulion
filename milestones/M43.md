# M43 — Extension navigation API

M43 extends the local JavaScript extension API from filesystem/editor access to
safe navigation of the notes view. Navigation is a host-owned UI capability:
extensions receive canonical note paths and narrow navigation results, never DOM,
CodeMirror, URL, or File System Access handles. The filesystem remains the source
of truth and the markdown bytes remain the user's own data.

## Design spine

- `notes.*` remains the file layer; `navigation.*` is the active-view/router
  layer. Navigating must not be implemented as an implicit `notes.read()` or
  `notes.create()` operation.
- Note identities are folder-relative POSIX paths. Inputs accept the existing
  optional `.md` convention and use the same traversal, unsafe-character, and
  `.brulion` protections as the note API; returned paths are canonical.
- `navigation.openNote()` behaves like ordinary in-app note selection: it
  serializes through the note controller, flushes pending editor changes through
  the existing mtime guard, updates the active editor/sidebar/recency/route, and
  never discards or silently overwrites a conflict.
- A missing target returns a result instead of prompting or creating a file.
  Creation stays an explicit `notes.create()` call followed by navigation.
- `navigation.resolveLink()` is a read-only adapter over the application's
  existing markdown-link, wikilink, anchor, and note-list resolvers. Extensions
  must not need to copy Brulion's path-resolution rules.
- The new surface is additive to extension API v1. New permissions fail closed;
  existing manifests and extensions keep working without requesting navigation.

## Proposed public surface

```ts
export interface ActiveNote {
  /** Canonical folder-relative POSIX path, including .md. */
  path: string
}

export interface OpenNoteOptions {
  /** Heading slug without the leading #. */
  anchor?: string
}

export type AnchorStatus = "not-requested" | "found" | "not-found"

export type OpenNoteResult =
  | {
      status: "opened" | "already-open"
      path: string
      anchor: string | null
      anchorStatus: AnchorStatus
    }
  | { status: "missing"; path: string; anchor: string | null }
  /** `path` is the active note whose pending save blocked navigation. */
  | { status: "conflict"; path: string }

export type LinkKind = "markdown" | "wikilink"

export interface ResolveLinkOptions {
  /** Source note path; defaults to the active note when omitted. */
  from?: string
  /** The target syntax being resolved; no syntax guessing. */
  kind: LinkKind
}

export type LinkResolution =
  | { status: "resolved"; path: string; anchor: string | null }
  | { status: "missing"; path: string; anchor: string | null }
  | { status: "external"; target: string }
  | { status: "invalid"; target: string }

export interface BrulionNavigation {
  getActiveNote(): Promise<ActiveNote | null>
  openNote(path: string, options?: OpenNoteOptions): Promise<OpenNoteResult>
  resolveLink(target: string, options: ResolveLinkOptions): Promise<LinkResolution>
}
```

`resolveLink()` receives the destination only, not the surrounding syntax or
visible alias. For example, `[[tasks/today#done|Today's tasks]]` passes
`"tasks/today#done"`; a markdown destination may be
`"../tasks/today.md#done"` or `"#done"`. `from` is the note containing that
link, so relative markdown paths and same-note anchors have a stable base. The
returned `anchor` is the fragment without `#`; resolution carries it forward but
does not verify that a matching heading exists. `openNote()` performs that
scroll attempt and reports its `anchorStatus`.

`resolveLink()` is read-only and composable with `openNote()`: it never changes
the active note, pushes history, creates a missing file, or opens an external
URL. An extension can explicitly create a `missing` target and then pass its
canonical `path` and `anchor` to `openNote()`.

`navigation:read` grants `getActiveNote()` and `resolveLink()`;
`navigation:write` grants `openNote()`. Navigation does not expose a browser
back/forward API, external-tab opening, folder picking, or automatic
`createIfMissing` behavior.

## Phases

- [x] **P0 — Contract and permission boundary**
  Add the navigation types, permissions, manifest validation, sandbox RPC
  methods, Authoring Kit declarations/contract/API reference, and diagnostics
  for missing permissions and unsafe arguments. Keep the public API additive to
  v1 and update the contract drift tests.
- [x] **P1 — Active note and `openNote()`**
  Inject a vault-bound navigation capability into the extension host. Route
  navigation through a serialized controller operation that revalidates the
  target against the filesystem, handles extension-created notes without
  waiting for a stale sidebar snapshot, preserves normal route/history behavior,
  scrolls to an optional heading, and returns `opened`, `already-open`,
  `missing`, or `conflict` without silent data loss.
- [x] **P2 — Shared `resolveLink()`**
  Accept a raw destination plus an explicit `kind` (`markdown` or `wikilink`)
  and an optional source-note `from`; do not guess syntax or interpret display
  aliases. Reuse `splitAnchor`, `resolveNotePath`, `resolveWikilink`, and the
  authoritative note listing for relative markdown, same-note anchors, and
  wikilink basename/path targets. Return canonical existing or missing paths,
  anchors, and explicit external/invalid classifications without changing the
  active note, opening a browser, or writing files.
- [x] **P3 — Browser validation and authoring examples**
  Cover permissions, sandbox/RPC serialization, active-note reads, route and
  anchor navigation, missing-note handling, mtime conflicts, vault switching,
  markdown and wikilink resolution, and the create-then-open flow in real
  Chromium/OPFS. Add concise examples for journal and link-following
  extensions to the Authoring Kit.

## Done =

An explicitly enabled extension can read the active note, open an existing note,
handle a missing target or pending-edit conflict without data loss, and navigate
to a heading anchor. It can resolve markdown and wikilink targets with the same
rules as Brulion's UI, including relative paths, basename/path resolution,
anchors, missing notes, external links, and invalid targets, then compose that
result with `openNote()` when it deliberately wants to navigate. The API is
permission-gated, documented in the Authoring Kit, covered by unit and browser
tests, and navigation/resolve operations never alter `.md` bytes except for the
normal guarded flush of pending edits caused by switching notes.

## Out of scope

- Automatic note-open/file-change triggers or a general extension event system.
- `next()`/`previous()` ordering APIs or direct browser `back()`/`forward()` calls.
- Automatic creation, deletion, moving, or rewriting of notes through navigation.
- Custom extension UI, arbitrary DOM access, external browser navigation, folder
  selection, or File System Access handles.
- TypeScript execution, package installation, network imports, or an in-app LLM.
